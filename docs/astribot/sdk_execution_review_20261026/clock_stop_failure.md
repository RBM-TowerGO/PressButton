# 执行期间校时失败与停止核验（2026-10-26）

故障目录：`outputs/s1b_deployment/live_2000_split_1793015998737407466`。

## 已确认的因果顺序

1. 启动握手成功。控制端接受 112 次预测、发送 2102 次模型指令，相邻预测原始期限的覆盖空档为 0。
2. 工作站后台校时的三个候选采样均未满足 50 ms RTT 门槛。旧实现直接抛出 `clock_monitor_failed:ValueError('clock_probe_too_slow')`，工作站随后请求 `/stop`。
3. 控制端记录的 `operator_stop` 是该停止请求的原因，不是最先发生的故障。SDK 停止调用约 0.024 ms 返回，`logical_stopped=true`。
4. 随后的反馈稳定核验失败。配置要求停止后 250 ms 内获得连续 100 ms 的稳定反馈，角关节速度阈值为 0.003 rad/s、位置波动阈值为 0.0002 rad。已有约 10 Hz 的合并诊断日志显示：停止后约 141 ms，右臂仍有 0.011971 rad/s 的速度；约 246 ms 仍有 0.003860 rad/s。不能把本次核验失败简单归为误报。

运行中的小型动作 HTTP 请求 RTT 中位数 23.10 ms、p95 53.75 ms、最大 66.89 ms。SDK 发送计时的间隔中位数 4.23 ms、p95 10.31 ms、最大 23.89 ms；控制线程跳过 250 个节拍。频率警告有对应的调度抖动证据，不能因为预测供给连续就宣布 SDK 250 Hz 调度通过。

## 修改

- `ClockMonitor` 仅将 `SlowClockProbe` 作为不可用于更新时钟的采样：保留上次有效校准及其原始过期时间，0.25 秒后重试健康采样。50 ms RTT 门槛、10 秒校准有效期、时钟跳变与身份校验均保留。持续采样失败仍会停止，不重试动作提交。
- 校时事件写入每轮三个 RTT 及是否接纳，便于区分偶发网络延迟与校准长期失效。
- 执行用 `RobotState(control_only=True)` 保留全部七个部件状态、三个受控部件的已接受指令及驱动故障订阅，取消未使用的命令诊断订阅和无关部件指令回读。反馈使用深度为 1 的最新值队列；原诊断模式保留完整订阅。
- `StopObserver` 保留停止限值，增加采样数、反馈间隔、窗口长度、各关节速度/位置波动与超限索引，写入 `stop_feedback` 事件和控制摘要。超过停止截止时刻才返回的反馈不能被判为按期停止。
- 终端优先显示工作站的触发故障，随后显示机器人停止核验结果；正常 `operator_stop` 不再作为 `execution_fault` 诊断标题。
- 启动前端口冲突会标明机器人端口号；尚未创建远端运行目录时不再尝试收集不存在的日志目录。

## 验证和边界

194 项 S1B 测试通过（42.97 秒）。新增真实 HTTP 慢采样测试覆盖暂时延迟恢复、10 秒校准过期、慢响应中的 boot 身份错误、真正时钟跳变。完整工作站脚本测试在执行中注入三个 65 ms 的健康响应，确认丢弃该轮采样后恢复校准并持续执行；使用真实 ZMQ/HTTP 和替身 SDK。停止测试保留持续运动拒绝，并增加截止时间之后返回稳定反馈仍不得通过。

机器人只读对比脚本及日志位于 `outputs/s1b_deployment/clock_stop_diagnostics_20261026/`。两种订阅模式分别运行 8 秒：进程 CPU 时间由 6.442 秒降至 5.087 秒（约 21%）；状态回调分别为 14042 和 14036，已接受指令回调由 14042 降为 6017。SDK 未导入，未调用控制权或运动接口。该对比证明监控负载下降，不证明真实 SDK 的频率警告已经消失。

新版实机 shadow 尝试在端口预检查时退出：机器人另有用户正在使用的 `astribot_image_service.server`，启用了执行控制并占用 6200。用户明确要求保留它，未终止、接管或修改该服务。本轮没有新的实机 shadow 通过记录，也没有真实 execute/物理停止验收。

校时导致的偶发误停已通过回归；物理停止在原保护限值内是否稳定、真实 SDK 调度抖动是否改善，仍需待机器人可用时现场验证，不能以关闭核验或放宽阈值替代。
