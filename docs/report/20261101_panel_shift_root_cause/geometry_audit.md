# 图像、坐标与执行链路复核

本次只读取已有记录和代码，未连接机器人、未发模型请求、未修改生产实现。核对对象为 `20261101_211122_639d06d8` 的全部 14 条已执行命令及其决策前观测。逐项结果见 [geometry_input_audit.json](geometry_input_audit.json)。

## 已核实的事实

- **14 轮当前图像没有错配或客户端缩小。** 对每轮请求最后一个 LIVE 观测的两张 Base64 图片解码，与该观测目录原图逐字节比较，28/28 相同。头图均为 1280×720，腕图均为 640×360。客户端没有裁切、镜像、调换相机。这里不包含服务端视觉编码器内部缩放的结论。
- **头图与腕图没有长时间错位的证据。** 14 轮相机 source timestamp 最大差为 46.956 ms，记录的 RGB/状态时间差最大 33.6 ms。相机采集代码选择离腕图最近的头图并拒绝超过 80 ms 的组合；状态采样也拒绝超过 80 ms。时间差并非零，但不能解释静止场景下连续多轮虚构按钮位于两指间。
- **成功案例与本次起始手部目标几乎相同，而面板位置明显不同。** 两次初始命令位置仅相差 `[0.04649, 0.16400, 1.68709] mm`。本次前 10 条动作的类型、数值，逐条与成功示范前 10 条完全相同。这是明确的轨迹重复事实；是否由示范模仿、当前状态误判或二者共同造成，不能仅凭相同序列断言。
- **当前按钮在头图很明显，腕图没有目标。** 人工查看第 12 轮原图：按钮位于头图右侧，明显不在任何可见手指前方；腕图只有墙面、反光和两根手指。成功第 10 步 after 则在两种视角均能看到发光按钮，头图右侧手指投影与按钮相交。图像投影本身不证明三维接触，但这两组画面不支持“同样已对齐”。
- **执行器确实保留完整三轴自由度。** `target_for_xyz` 逐轴累加毫米到米，未做坐标旋转、轴交换或限制为 X；SDK backend 原样传递参数给共享执行器。既有真实第 8 条 `[0,-20,0]` 的实测位移约 `[1.02,-19.24,-0.03] mm`，支持横向运动路径有效。单个动作的前后实测不是严格到位误差评估。

## 真正存在的几何契约缺口

1. **模型知道 SDK 末端在哪里，不知道接触指尖在哪里。** 当前 `reference_point` 是 `sdk_end_effector`，末端四元数与位置不是某根手指的接触点；夹爪开合值为 SDK 原始单位。观测中的 `tcp_pose` 和 `tcp_surface_gap_mm` 明确为 `null`，没有暗中完成指尖转换。
2. **只有机器人轴定义，没有实测的图像运动关系。** 工具已说明机器人右是 `-Y`，但没有相机到机身外参、可见指尖标定、局部图像 Jacobian 或经过验证的“该视角移动 -Y 后哪个特征往哪里走”。深度和彩色相机间的工厂配准不能代替相机到机器人的标定。
3. **没有程序维护当前对齐误差和纠偏进展。** 动作参数解析只验证工具、字段、有限数值；它不计算按钮与接触指的图像误差，也不核验理由中的位置描述。因此结构合法的 `[5,0,0]` 可以一直通过。这个行为符合此前“不增加视觉硬门控”的设计，不是隐藏执行器 bug。
4. **历史成功没有全量实测状态。** 成功录制仅包含命令目标与相机/深度记录；其头部第 1 步命令为 `[0,30]°`，没有可直接引用的实测头角。当前本次头部观测约为 `[-0.7,24.9]°`。因此不能将成功命令头角当成成功相机精确外参；也不能以两者差异断言硬件异常。

这些缺口主要影响可重复的接触点对齐、毫米步长和跨视角转换。它们**不足以单独解释当前明显偏右时仍连续向前**：既有实验只提供当前视觉事实、没有新增坐标映射，就能使同一个动作模型生成 `-Y`。这更支持优先检查“当前视觉状态如何进入并约束决策”，而不是把故障直接归为 SDK 不会右移。

## 输入表现的次要风险

成功拼图将 1280×720 头图等比缩为 640×360，腕图保持 640×360，四幅放进 1280×792 的一张图，JPEG quality 95；没有裁切。示范细小接触关系会比当前头部原图更小。当前图仍是完整分辨率，且偏移明显，因此尚无证据将当前持续前推归因于客户端缩图。服务端实际视觉分辨率需要另行核对。

当前生产系统提示与头部工具已明确：转头改变头部视角，不改变腕相机相对手的位置。最近 5 图实验却仍返回“降低 pitch 使腕相机看到按钮”。这是模型输出违反已给契约的实例，不是接口把头部命令误执行为手部移动。
