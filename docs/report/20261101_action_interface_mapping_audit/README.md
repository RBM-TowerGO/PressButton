# 任务接口与空间到动作转换排查

日期：2026-11-01。来源：`20261101_211122_639d06d8` 第12、13、14轮决策请求（目录 `0011`、`0012`、`0013`）。

本次排查只读取既有运行记录、运行模拟后端测试，以及向已有 `qwen38` 服务发送保存图片的推理请求。没有连接机器人或执行模型建议，没有修改正式提示词、动作工具或执行器。代码中原有未提交修改保持原样。

## 1. 排查问题

区分三个环节：

1. 当前图像 → 目标与夹爪的相对位置、可见性、对齐状态。
2. 相对位置与任务阶段 → 机器人应该向哪个方向运动。
3. 机器人运动方向 → `[X,Y,Z]` 参数 → SDK 命令目标。

原报告中定位请求的 `next_axis=+Y` 错误，只能说明该请求里的空间到动作转换失败；不能直接证明原动作会话的持续 `+X` 前推也是由同一个符号错误造成。

## 2. 执行链路检查

链路为 `propose_move.xyz_mm` → `RobotClient.execute` → `Service.submit` → `SDKBackend.move` → `CommandExecutor.prepare` → `target_for_xyz` → SDK 发送。

- 三轴数值在上述 Python 链路中没有轴交换或符号翻转。
- 目标位置计算为 `previous_command_pose[i] + xyz_mm[i]/1000`。位移是机身坐标增量，没有按手部四元数旋转到工具坐标。
- 位置增量累加到上一命令目标，四元数保持不变，与系统提示词一致。
- `head_deg` 是绝对角度，经度到弧度转换后送给头部关节；与手部平移是不同接口。
- 解析器检查工具名、字段、向量长度与有限数值，不检查理由中的方向与数字是否一致。

执行器相关既有测试：

```bash
.venv-data-review/bin/python -m pytest \
  tests/test_shared_keyboard_agent.py tests/test_agent_loop.py \
  tests/test_s1b_keyboard_direct.py tests/test_conversation.py -q
```

结果：**93 passed in 16.49s**。另对具有90度绕Z旋转姿态的合成目标执行六个有符号位移计算检查，确认四元数不影响机身轴增量。[检查记录](interface_audit.json)

既有真机日志也支持命令数值没有被颠倒：第8轮 `[0,-20,0]` 的命令目标变化为 `[0,-20,0]`，观测到的实测位移约为 `[1.02,-19.24,-0.03]` 毫米；第12轮 `[5,0,0]` 的实测位移约为 `[4.03,-0.02,0.10]` 毫米。实测前后帧不是严格到位测量，但方向与下发轴一致。[逐轮记录](recorded_motion_deltas.json)

这些检查不等于重新标定物理坐标，也不能验证未执行的新建议的效果。

## 3. 发现的接口缺口

| 位置 | 发现 | 含义 |
|---|---|---|
| 动作工具 schema | `xyz_mm`、`head_deg` 没有字段描述；函数描述基本只是名称 | 单位、参考系、左右符号依赖系统提示词 |
| 模型会话精简 | `model_context.session` 省略服务端已有的 `coordinates`、`motion_units`、`head_units` | 模型看到的结构化会话不包含这些契约；系统提示词仍有相关定义，不能说完全未提供 |
| 相机与机身关系 | 模型输入不含相机到机身变换、图像误差到机身位移的映射或接触手指标定 | “图中右侧”到“机器人右侧”仍由模型结合画面推断 |
| 头部关节 | 提供了 `[yaw,pitch]` 和绝对角度，但未说明正方向、关节范围 | 无法把此前转头建议视为已经验证正确 |
| 输出检查 | 只验证结构和数值有效性 | 理由正确而轴/符号错误仍可通过解析 |

相机服务中的工厂 `rotation/translation` 用于深度和彩色图像配准，不是相机到机身的外参。不能拿它直接完成机器人空间转换。当前帧选定深度区域无有效值，也没有可用的已标定按钮接触点。

代码依据：[工具与解析](../../../src/pressb/agent_loop/client.py)、[模型会话精简](../../../src/pressb/agent_loop/model_context.py)、[服务端会话](../../../src/pressb/agent_loop/service.py)、[共享执行器](../../../scripts/s1b_keyboard_control.py)、[相机配准](../../../scripts/s1b_camera_view.py)。

## 4. 对照设计

三帧来自同一次失败运行，相机姿态相同，末端沿X前进。逐帧检查原图后，均标记为头图目标在夹爪右侧、腕图目标不可见、未对齐。[离线标注及来源](labels.json)

每帧保留原系统提示、完整历史、全部图片、状态和动作工具，只做以下干预：

| 条件 | 唯一干预 |
|---|---|
| A 原始请求 | 完全不改 |
| B 坐标说明 | 末尾追加机身六方向与坐标符号对应关系，区分手部运动与图像物体运动 |
| C 视觉事实 | 末尾只追加4个离线图像判读字段，不给机器人方向、轴、位移幅度 |
| D 视觉事实＋坐标说明 | 组合C、B的相同消息，先C后B |
| E 工具字段说明 | 把B的相同坐标说明放在 `xyz_mm.description`，不追加用户消息 |

这里的C、D是**提供正确中间状态的干预**，不是独立感知流水线的端到端验证。它们用于判断：当当前位置被明确提供后，原动作模型能否自行选对轴与符号。

另用原系统提示及原动作工具，去掉图片和动作历史，分别要求把“机器人手部向右/左/前/后/上/下10毫米”翻译为命令。这6次请求只检查已知机器人方向到数字参数的编码能力，不检查相机到机身的几何转换。

模型标识与服务信息保存在 [models.json](models.json)。温度0、关闭thinking、最大输出512 token均沿用原请求；每帧每条件只调用一次，条件顺序轮换，不清空共享缓存。三帧相关性很强，不能当作三个独立任务成功样本。

## 5. 结果与解释

原始输出逐条保存在 [report.json](report.json) 和 `tests/*/response.json`。15次视觉动作请求与6次纯坐标请求均完成，没有请求错误，均返回单个工具调用。

| 条件 | 第12轮 | 第13轮 | 第14轮 |
|---|---|---|---|
| A 原始请求 | `[5,0,0]` | `[5,0,0]` | `[5,0,0]` |
| B 坐标说明 | `[5,0,0]` | `[5,0,0]` | `[5,0,0]` |
| C 视觉事实 | `[0,-10,0]` | `[0,-10,0]` | `[0,-10,0]` |
| D 视觉事实＋坐标说明 | `[0,-10,0]` | `[0,-10,0]` | `[0,-10,0]` |
| E 工具字段说明 | `[5,0,0]` | `[5,0,0]` | `[5,0,0]` |

全部是未执行的毫米位移建议。A、B、E仍错误描述“腕图按钮位于两指之间”。C、D改变了方向，理由也反映当前位置；其中第13轮C的简短理由未提到腕图，因此不能说所有纠正后的理由都完整覆盖双视角。

**6个纯方向编码请求全部正确**：right→`[0,-10,0]`、left→`[0,10,0]`、forward→`[10,0,0]`、backward→`[-10,0,0]`、up→`[0,0,10]`、down→`[0,0,-10]`。只使用原系统提示中的坐标契约，没有额外提供六方向对照表。

这组结果支持：

1. 模型在明确知道机器人运动方向时，能把六个方向编码为正确参数；“完全不知道右是-Y”不是这次持续前推的充分解释。
2. 单独增强坐标文字，或将其放到工具字段说明中，都没有改变这三帧的错误行为。工具契约欠明确是真实的接口缺口，但本次补足它并未修复主要现象。
3. 在不新增坐标提示的C条件，提供当前相对位置与可见性就足以令原动作模型选出-Y。这比旧实验“定位结果＋坐标提醒同时加入”更直接地定位到了当前状态进入动作决策的环节。
4. 这不证明模型内部一定先选动作再生成理由，也没有排除历史模仿、任务阶段判断、当前证据提取与提示位置等更细的机制。
5. 仅能说这些动作建议更符合需要横向纠偏的当前场景，不能说10毫米幅度正确、完成接触或按键成功。

## 6. `next_axis` 与单次结构化输出的补充试验

仅用第12轮追加4次请求，没有提供上述离线视觉标签。[完整记录](interface_probes/report.json)

前三次沿用旧定位脚本的系统提示、定位问题和工具，只使用当前观测、不带案例和动作历史。它们的视觉判断均为“头图按钮在右、腕图不可见、未对齐”。

| 条件 | 改动 | 结果 |
|---|---|---|
| 原始 `next_axis` | 不改，无字段描述 | `+Y`；理由却说明应向机器人右侧移动 |
| 明确手部运动轴 | 仅在 `next_axis.description` 说明它指手的期望位移，不是当前位置或目标在图中的运动，并列出正负符号 | `-Y`；理由与方向一致 |
| 语义方向 | 将 `next_axis` 换成带语义说明的 `robot_hand_direction`，枚举为自然语言方向 | `right`；理由仍出现一次“+Y? actually … -Y”的自我修正 |

因此，用户指出的 `next_axis` 问题确实能通过接口说明修正，不能把这个字段错误简单等同于模型不会方向转换。不过该干预同时增加了手部运动语义和明确符号，尚未进一步区分二者的贡献；单帧一次也不能证明可靠性。

第四次保留完整动作历史，只在 `propose_move` 参数中增加4个必填字段：当前头图相对位置、腕图可见性、对齐状态、预期机器人运动方向；不提供正确答案，不改变原图片或系统提示。

结果：模型只返回原来的 `xyz_mm` 和 `reason`，**漏掉全部4个新增必填字段**。建议为 `[0,0,-5]`，理由仍错误声称腕图按钮在两指之间。这是一次违反实验工具字段契约的响应，不能算“结构化单次推理已修复”。`single_tool_without_prose=true` 仅表示返回了单个工具调用，不代表参数满足schema；补充字段校验明确记录了错误。

该结果表明，在这次服务配置与历史上下文中，仅声明 `required` 没有保证模型返回这些字段。正式解析器会依据其已知工具定义检查字段，但若要引入新格式，schema与解析器必须一起更新，并处理缺字段或语义冲突。实验格式尚未接入正式执行链路。

## 7. 排查结论与下一步优先级

**模型已有完成关键子步骤的能力；当前失败更集中在“当前图像状态如何约束动作选择”，同时存在可被接口说明修正的方向字段错误。两者不应混为同一个正负号问题。**

证据链是：执行代码与既有位移记录未显示反号 → 无图六方向编码全部正确 → 修正定位工具字段语义可得到-Y → 但完整动作请求只补坐标仍前推 → 明确提供当前视觉事实即可改变动作轴与符号。

建议按以下顺序继续，而非直接更换模型或认定必须使用多个Agent：

1. **补全接口契约。** 在工具字段和结构化会话中提供单位、机身参考系、增量/绝对值、手部运动含义；头部正方向应依据硬件资料或已有测量确认。此次结果显示，这一步能纠正定位字段，但单独不足以解决前推。
2. **让当前状态成为可检查的输出。** 分别记录图像相对位置、机器人期望运动方向、数字参数，绑定当前观测ID；检查字段完整性和方向/数字一致性。只追加 `required` 或“认真看图”不够。单次调用与分两次调用仍需比较，不能把本次失败的单一schema试验推广为单次调用不可能。
3. **把确定性符号转换交给代码。** 已明确的 `robot_right` 可确定转换为 `-Y`，减少模型重复处理符号的负担。但这只解决机器人方向到参数的编码，不能将任意相机的 `image_right` 直接写死为 `-Y`。
4. **验证相机到机器人及毫米幅度的映射。** 基于标定或记录中可验证的动作—图像变化关系，进一步区分视角、接触手指、误差方向和步长；本次没有验证10毫米是否合适。

本次共25次模型请求，只有24次满足已检查的字段与枚举契约；21次原动作格式响应还通过了正式 `parse_proposal`。新增单次结构化动作请求因漏字段失败。所有建议均未执行，三帧来自同一次失败运行，尚无跨任务泛化或真机完成结论。
