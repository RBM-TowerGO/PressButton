## 结论

这次是 `get_view` 阶段持续增加头部俯仰角。**主要问题是上一轮新增的取景放行条件过强，而取景阶段没有相应的进展检测和恢复分支。** 条件要求头部图像同时完整定位按钮及白箭头所指精确物理指端；模型一直无法确认后者，因此所有手部工具持续被移除，动作 Agent 反复选择继续低头。另有实际头部角度长期未追到命令目标的异常，以及最后终止运行的服务并发错误。这三件事需要分别处理。

没有发现客户端漏图、串图、重复使用旧帧。单图／灰图探针也支持图片内容确实影响模型回答；同时暴露模型漏认明显对象，不能把链路正确当作识别正确。

本地进程检查时 Agent 和机器人服务子进程已退出，网页启动器仍存活。最后停止请求已返回 `STOPPED`。

## 为什么会持续低头

`view_acquisition.validate()` 的 `usable_head` 要求 HEAD 面板可用、按钮完整、物理接触端完整，并有合法框／点。五轮均无法满足接触端条件。`Conversation.body()` 因而只提供 `propose_head`、`request_observation`、`report_unable`；即使腕图已能提供接触参考，模型也不能进入手部对齐。

查看原图，初始头图已能看到面板和按钮，但手指在底部被裁。后来头图已能看到两只夹爪及右手手指，浅色箭头呈很小的侧面窄条，不像腕图中的标记那样醒目。模型仍给出 `head.arrow_box=null`、`contact_tip=null`。这里既有细小标记识别遗漏，也有把精确接触识别强加给全局头部视角的设计问题。

同时，已有进展监测针对XYZ移动；head／gripper被视为比较段结束，`get_view` 也提前返回，不执行该监测。因此持续30→35→42→48→55°不会触发取景停滞复核。整个运行未出现 `progress_review` 或 `conflict.json`；上一轮增加的“双方观点冲突恢复”没有机会参与。

取景模型一直判断“指端不可辨”，动作模型照此继续低头，二者没有显式分歧。**这次循环与模型不遵守提示不同：它在遵守程序限定的取景流程，而这个流程缺少可达性判断。** 动作模型仍可报告无法继续，但没有选择它。详见 [决策审查](decision_audit.json)。

## 头部目标与实测为什么持续不同

不仅采图时实测落后；下一条动作开始前，模型推理已经等待约47–65秒，实测仍未达到上一目标：

- 前目标30°，约64.76秒后下一动作开始实测25.12°。
- 前目标35°，约47.47秒后实测28.84°。
- 前目标42°，约63.45秒后实测34.69°。

所以不能只用“拍照太早”解释。共享执行器在head插值结束后只发送最后目标一次，随后清除active，下一控制周期恢复仅arm＋torso的Cartesian保持；head目标不继续发送。实际调用使用`control_way='filter'`，这与长期欠跟踪构成需要优先验证的执行层疑点。

当前机器人端可读SDK包装与本地归档哈希一致，但包装仅转发参数，实际过滤与控制组切换在编译的`.so`中。纯fake确认了调用顺序，**没有证明SDK一定取消了head目标**。物理因果还需单独验证，不能用fake或增加固定拍照延迟代替。见 [SDK交接审查](sdk_head_handoff_audit.json)。保持“发送完成”的现有语义，与排查目标保持问题是两件事。

## 503终止原因

`Service.task()` 持`self.lock`进行`deepcopy`，但worker `_run()`在更新任务的motion字段、observation_url和错误信息等位置没有持同一把锁。纯本地fake在复制期间新增字段，稳定复现相同的`RuntimeError: dictionary changed size during iteration`。

这是已确认存在的服务竞态，很可能解释本次503；HTTP handler没有保存现场traceback，因此不宣称已获得现场精确抛错堆栈。该错误发生在持续低头之后，不是此前循环的原因。客户端收到错误后停止，没有重放动作。见 [并发复现记录](snapshot_race_reproduction.json)。

## 修复顺序建议

1. 修复服务任务快照与worker发布之间的并发访问，并保留异常堆栈，保证已执行动作的结果能被准确取回；不要通过重复提交动作补日志。
2. 验证共享执行器的头部目标保持和控制分组切换，键盘／Agent共用同一实现，明确发送目标与实测响应。
3. 重新定义取景职责：HEAD确认面板、目标及手部的大致位置；WRIST承担白箭头与具体接触端的局部定位。不能把HEAD精确辨认小标记作为所有手部调整的唯一前提。细定位未知仍应显式保留。
4. 给get_view本身增加实际进展检查：记录目标与实测角度、可见区域是否扩大、缺失对象是否真的入镜；持续改变角度而没有新增可用信息时，进入有针对性的恢复／报告，而不是自动继续增加pitch。

本次未修改控制逻辑或重启真机。以上结论区分了已核对事实、助手对保存图的审查及待验证的执行层假设。
