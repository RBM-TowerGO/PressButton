用户要求：修正次数不要设置上限。本次代码修改没有启动机器人，也没有额外调用实际模型；使用真实失败记录确定问题，再用模拟模型、SDK和HTTP测试验证流程。

## 本次为何失败

运行 `20261102_120741_0ca36af5` 已停止。完成10条移动，未发过头部命令：第1–3轮各+Z10，第4轮+Y10，第5–7轮各+Z10，第8轮−Z10，第9–10轮各+X10。第11轮未执行。净命令位移[X+20,Y+10,Z+50] mm，实测净变化约[+16.60,+10.76,+49.94] mm。头部pitch始终约0.787°。

1. 提示词已加载白箭头和先获得完整HEAD视野的要求，但模型第一轮仍引用高度先验直接选择+Z；程序没有把初始视野作为必须完成的阶段。[初始头图](images/round_1_head.jpg)中按钮与接触指端未完整入镜。
2. 独立复核发生了明显误判。第8轮把按钮说成在指端下方，动作模型据此改为−Z；[对应腕图](images/round_8_right.jpg)中按钮仍明显在箭头所指前端上方。这说明复核有输出并不等于输出正确。
3. 第11轮先提出+X10，因腕图两指不可确认而被前推检查拒绝。原有唯一修正机会被用于改成+Z5；该候选的last_effect=unchanged又触发新的进展复核。新复核认为按钮在右，候选说居中，程序以冲突退出。新复核在第二次动作响应之后才生成，模型根本没有机会阅读它再调整；第11轮repair-request里只有旧第4/8轮的复核。
4. 退出检查范围还涉及不同模型的横向判断不一致，并非“重复同轴”本身：最后候选为+Z5，上一实际动作为+X10。该复核的视觉观点不是事实真值。

各模型调用累计约326秒，10条运动发送约9.44秒，因此现场感觉等待多、移动少。当前图片与对应保存观测一致，动作响应ID均不同；SDK发送均完成。退出原因是候选校验，频率警告不是本轮退出原因。

结构化记录见[运行审查](run_audit.json)，原始运行未改写。

## 本次修改

- 动作候选、独立判读/进展复核、前推检查、亮灯/撤回核验、上下文压缩的格式修正均不设次数上限。
- 新复核产生后，反馈进入下一次动作请求；不再因为前一个检查已经用过一次修正而退出。
- 直到得到合法结果、模型报告无法继续/完成、人工停止或真实网络/模型请求错误才离开相应流程。网络故障仍沿用现有报错处理，不变成无限网络重试。
- `--max-rounds`仍控制外层决策轮次；内部修正不消耗这个轮数，也没有另加修正次数上限。
- 修正中的候选不执行。命令幂等、观测绑定、前推检查、q/Ctrl-C及迟到响应检查仍生效。
- 原始响应按response-N保存，校验按validation-N保存，修正请求按repair-request-N保存；保留repair-request.json指向最新内容。网页按数字选择最新响应，展示累计请求/修正次数、状态及最近原因。
- 修正输入保留原有效上下文和最新修正反馈，不无限累积此前所有非法输出；完整尝试仍保存在日志。

这次修改针对修正机会耗尽的接线问题。没有把先低头改为程序强制阶段，也没有宣称已解决独立视觉复核误判。
