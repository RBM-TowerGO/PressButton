`--operator-present --estop-ready` 表示现场操作人员在位且急停就绪。默认 600 秒，`--duration` 可调整，Ctrl-C 请求停止。此命令会申请控制权并实际发送通过约束校验的动作。默认不交接已有控制权；若其他节点持权，入口报 `control_rights_already_owned`。明确需要正常交接时加 `--request-control-handover`，不使用高优先级抢占。

若出现 `control_rights_unavailable` / `control_rights_already_owned`，且准备将已有控制器的控制权交给本次模型执行，使用：

```bash
.venv-astribot-inference/bin/python scripts/start_s1b_inference.py \
  --checkpoint 2000 --mode execute --operator-present --estop-ready \
  --request-control-handover
```

控制权检测同时查询 `/astribot/control_rights` 服务可用性：节点级 ROS 图有时不返回所属节点，不能据此认定无人持权。显式交接等待服务返回 `success` 且原持权服务消失，再创建 SDK 客户端；不会自动回答 SDK 的强制接管提示。SDK 输出 `acquired control rights` 也不代表真实取得权限，入口始终核对 `get_control_rights_status()`。

执行流程：

1. 校验 10 维接口、模型身份、执行配置、SDK commit、实测状态、已接受指令及控制权。
2. 收到首个有效预测后申请 SDK 控制权。初始化期间的旧预测丢弃；最多保持硬件原有目标 1 秒，等待新的有效预测。
3. 模型动作时间线仍是 30 Hz；独立 SDK 线程按 250 Hz 采样队列并发送 `control_way="filter"`。同一个预测点只在原始截止时间之前重复使用，过期后选择后续有效点，末点过期立即停止，不能延长旧预测。夹爪按 0.5 阈值解码为 0/100。
4. 首个新预测到来后，以 `startup_blend_seconds=2.0` 从硬件已接受的保持目标渐进切入。使用五次多项式系数融合每次新鲜预测，固定目标情况下两端速度/加速度为零；变化目标的平滑交给 SDK filter。过渡中仍检查硬件位置、状态新鲜度、驱动错误和预测期限；未控制部件漂移仅报告 warning。日志写入后再次检查期限。
5. 队列耗尽、模型身份变化、断网、控制权丢失、状态异常或 Ctrl-C 都会停止消费旧队列。队列耗尽是否立即停机由 `queue_exhausted_action` 决定（默认 `stop`；当前 VLA 配置为 `hold`，见本文末节）。独立 100 ms 看门狗保留；不会在执行模式中自动重连恢复运动。
6. 退出时核验停止反馈、释放控制权、关闭状态监视器。即使停止反馈核验失败，也尝试释放控制权。

本地日志：`outputs/s1b_deployment/live_2000_*/`。机器人日志在启动器对应的 `outputs/live_*/` 中：`events.jsonl` 保存实际 SDK 目标、状态和停止原因，`ticks.jsonl` 保存模型原始动作、夹爪解码目标、过渡目标、SDK 输入目标、过渡系数、选择步号和发送时间。这里的 `sdk_target` 是传入 filter 的目标，并非 SDK 内部滤波后的最终硬件命令；硬件命令回读单独记录。`summary.json` 的 `sent_commands` 包括启动保持，`model_commands` 计使用模型目标的 SDK 调用次数（包含启动过渡和同一有效目标的重复发送），`policy_targets` 计所选择的不同 `(observation_id, step_index)`，不能把这些 SDK 调用次数误当推理次数。`control_loop` 记录请求频率、实际 tick 数、错过 tick 数和最大调度偏差。无模型动作下发会报执行未完成。

## HTTP 生命周期修复

`live_2000_1793001241974705873` 的首个模型执行请求在 SDK 初始化后遭遇 `RemoteDisconnected`。原服务端连接空闲超时为 5 秒，SDK 初始化期间继续保留 HTTP keep-alive socket，后续请求复用了已关闭的连接。现在 health 和 predict 都采用单请求连接，响应读取后主动关闭 socket；下一次请求建立新连接。该修改不自动重试不确定的预测请求，也不改变 session 或跳过模型身份校验。新增真实 HTTP 服务测试复现旧连接失效，并验证相同等待时间后新连接成功。

启动保持阶段网络失败时现在直接通知实际执行器 fault，不依赖尚未绑定执行器的调度器，停止原因保留为网络失败。

上述运行只发送了 1 次保持指令，模型动作 0 次；同时记录到停止反馈未在 250 ms 内满足稳定判据。HTTP 修复不能被视为该物理停止反馈问题已解决，也不能作为真机闭环通过证明。

## 官方实时控制示例整理

- 默认模型配置固定 `control_way: filter`、`sdk_frequency: 250`；不调用 `set_filter_parameters` 改写 SDK 默认滤波参数。
- 250 Hz 应用线程使用单调时钟和可中断等待，避免网络请求阻塞目标发送；错过的周期不会补发成突发命令。该频率是调度目标，不是 Linux/Python 硬实时保证。
- 启动过渡 2 秒借鉴官方轨迹回放的首点过渡时长，但实现为对实时新鲜目标的显式渐进融合，并不声称与 SDK waypoint 规划算法等价。没有执行全身 home，也没有将预测改成阻塞式 waypoint 回放。
- 独立 100 ms 命令看门狗仍在；网络请求未返回时，已有预测过期会由 250 Hz 线程停止执行。驱动错误、状态过期和操作停止同样锁存，恢复正常消息不自动重新运动。
- 本地使用真实 HTTP 服务、协议编解码、调度器、执行线程、真实 guard 与替身 SDK 联合验证推理延迟期间的重复采样发送、超出 horizon 的停止和迟到响应拒绝。没有运行新版本真机运动，原驱动代码 `13243026` 和停止反馈问题不据此宣告解决。

## 观测匹配导致请求中断的修复

用户再次提供的附件包含 `live_1793007590172285931` 的旧日志溢出与 `live_1793008090236990288` 的预测队列耗尽。后者 `log_writer.error=null`；最后 observation 435 在 `20064168687267` 收到，预测在 `20064327691052` 返回，原预测末点截止 `20064402020600`，停止发生于 `20064403753596`。响应返回后只剩约 74 ms，后续没有 prediction_request。整场记录了 48 次 skew_arm，但采样诊断不能精确重建每次拒绝的完整历史。

发现 ObservationBuffer 只尝试最新头部帧：最新帧无法匹配关节状态时，即使缓冲中有未使用且仍新鲜的完整观测也会直接拒绝，造成不必要的请求空档。现在从新到旧寻找最新可匹配帧，保持原 80 ms 接收新鲜度、10 ms 关节源时间偏差和 40 ms 右相机偏差；不重用已提交帧。摘要 selection_counts 记录候选匹配失败与 aligned_older_head 次数。拒绝时每 100 ms 记录一次原因、最新来源时间和最后已用序号，便于定位余下的供给空档。

回归验证最新帧落入状态空档时能使用未用的有效前帧，旧帧过期或已提交时不能使用，且补齐反馈后恢复最新帧。此修改修复一个明确的请求阻断路径，不等同于证明真机整个控制链已稳定；没有修改预测 horizon 或停止反馈判据，也未启动真机运动。

## 2026-10-26 21:10 预测耗尽改为保持（用户明确要求）

`live_2000_split_1793019449530740210` 的 5.3 秒 execute 运行在 observation 2508 之后出现供给空档：2508 末点截止 `31448600543613`，下一批预测返回时控制端已在 `31448601945930` 因 `queue_exhausted` 锁存停止，工作站随后收到 `control_session_inactive`。按用户“去掉这个安全停机机制”的要求，只取消“预测 horizon 耗尽即锁存停机”这一条。

配置项（执行配置，不是启动参数）：

```json
{"queue_exhausted_action": "hold"}
```

- `hold`：250 Hz 线程抽不到可用预测点时，把 guard 已接受的最后一个目标原样重发给 SDK（`LiveExecution.hold()`，与启动保持同一路径），继续等待新预测；新预测到达后自动回到模型跟踪。不重发队列里未下发的过期点，不把预测 deadline 从到达时刻重新起算。
- `stop`：原行为，`ScheduleError('queue_exhausted')` → `executor.stop()` 锁存 FAULT。代码默认仍是 `stop`；旧探针配置和未显式设置该项的配置不受影响。
- 其他停机路径全部保留：状态过期、驱动错误、控制权丢失、命令看门狗、日志写盘失败、Ctrl-C、`/stop`、急停。
- 可见性：每次保持发一条 `servo_tick`（`covered=false`、`held=true`、`reason=queue_exhausted|no_point_in_tick_window`），并按秒限频记录 `prediction_starvation` warning；`robot/control/summary.json` 的 `control_loop` 新增 `starvation_action`、`starved_ticks`、`max_starvation_ns`，调度器计数新增 `starved_servo_ticks`。

残留风险（明确记录，不声称已消除）：保持会以 250 Hz 刷新 100 ms 命令看门狗，因此**预测流/网络长时间中断时机械臂不会自动停，而是停在最后一个已接受目标上等待**；机械臂仍可能继续走完到该目标的有限行程。现场急停、操作员与 `Ctrl-C` 仍是唯一的人工兜底。要恢复原行为，把该配置改回 `stop` 即可。
