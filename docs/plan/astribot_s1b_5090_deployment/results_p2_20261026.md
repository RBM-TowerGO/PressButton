- 工作站推理服务及机器人反向 SSH 隧道都只监听 `127.0.0.1:8796`。握手核对 `s1b-joint10-v1`、10 维/7 步、step 2000、model SHA `522b6425d3c71b43d1b41fb72e5468c9dbe5619828211501c3b12136e38ce99d` 和 data contract SHA `3a4c776dab3d97b0634ec782eb464145a8a6c1b50f305a32e173c60bb914345c`。
- SDK 当前 commit 复核仍为 `2644cdfba47f3dd311d923b172ac6c24909f6fda`；相机驱动日志版本为 `9b03bf7`。机器人为 Python 3.10.12 / NumPy 1.24.0 / OpenCV 4.11.0 / ROS Humble，domain 25；没有安装/更新依赖或升级 SDK。
- head 为 `head_rgbd`，序列号 `CL8T75401HG`，1280×720；right 为 `right_wrist_rgbd`，序列号 `408623070739`，640×360。已检查回放画面和对应视角，不使用 head_stereo。
- `CameraImage` 有尺寸/共享块信息但 `image.data` 为空，不能直接作为像素。采集既有 JPEG topic，经 OpenCV 解码并在边界转换 BGR→RGB 一次；HTTP 仍传 uint8 原始 RGB，不二次 JPEG 编码。

ROS 图证据确认桥接器仅订阅以上五个传感器 topic，只有 ROS 自带 `/rosout`、`/parameter_events` 发布和参数服务，没有应用/运动 publisher、服务客户端或 action 客户端。执行入口在导入 ROS 前即拒绝启动。启动相机所调用的是传感器专用 SetBool 服务，不是 SDK 运动控制初始化。

五路源 header 和接收 monotonic 均严格递增。以机器人 wall→monotonic 固定 offset 映射 epoch header，整个运行的采样 offset 范围为 0.199 ms，未触发 5 ms 跳变门槛。轻微负状态年龄最低约 -0.077 ms 属于已保留的时钟/采样偏差，没有截断。该映射仅证明当前记录时间域可比较，不证明物理曝光或执行时刻已经标定。

## 相机故障与限定修复

1. 相机服务返回 ON 后，初次 15 秒短测仅有状态流，有效预测为 0；桥接器拒绝缺流，没有生成假图像。
2. 恢复原始全相机配置后，15 秒短测完成 104 次请求；随后长测仅连续有效 316.253 秒、2,713 次请求，相机主进程在 JPEG 格式错误后发生 segmentation fault。该轮失败，原始日志保留。人工中断这轮还暴露出 rclpy 重复 shutdown 的清理异常，现已修正。
3. 独立副本只保留 right RGB 和 head RGBD 设备。尝试将 head 改为 RGB-only 导致 `bad_optional_access`，关闭原始 depth publisher 槽的组合也未通过；均未用于最终验收。最终保留原始 head `CameraType=3` 和全部原通信配置，只减少实际设备列表。
4. 最终双相机主进程在 GDB 下运行以捕获崩溃，未再出现上述 JPEG 错误或段错误，并完成本报告的 610 秒运行。`prepare_s1b_cameras.py` 可重建副本，生成结果与实际运行副本逐文件 hash 一致。没有修改/替换系统二进制、共享库或全机配置。

不能据此断言厂商崩溃根因已定位，也不将原始全机配置或未经复测的不同相机组合作为已通过方案。后续运行须使用本次核验的副本；P3 应在目标运行条件下继续长测。
