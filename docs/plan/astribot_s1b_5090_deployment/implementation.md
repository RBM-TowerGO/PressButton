# joint10 有线部署实现规格 v1.0

本文保留完整部署规格。P0/P1 已实现 `contract`、`policy`、`protocol`、`server`、`recorder` 以及配置审计、离线评估和本机服务入口；参见 [操作手册](operations_p0_p1.md)。机器人桥接、观测、调度、执行器及 analyze 模式仍为拟新增接口，不能作为现有命令使用。

## 1. 模块与配置

在 `src/pressb/s1b_deployment/` 下实现 `policy`、`protocol`、`observation`、`scheduler`、`executor`、`recorder` 六个职责模块。新增入口：

| 入口（实现状态见说明） | 参数与职责 |
|---|---|
| `scripts/s1b_policy_server.py` | `--run --checkpoint --config --device --port`；5090 推理服务，显式选择 2000／8000，不硬编码 step 8000 |
| `scripts/s1b_robot_bridge.py`（待实现） | `--config --mode shadow\|execute`；机器人端采集、请求、调度及可选 SDK 执行；默认 shadow |
| `scripts/eval_s1b_deployment.py` | `--mode offline --checkpoint 2000\|8000 --config --output`；离线推理已实现，analyze 日志分析待实现 |

配置模板放在 `configs/s1b_deployment_v1.yaml`。按模型、网络、采集、调度、SDK、约束、日志分组，禁止存放 SSH 密码。执行所需的尚未确认字段使用 `null`，配置检查要列出所有缺项并拒绝 execute。保存 resolved config 及其哈希，不在代码中隐藏限值。

服务默认 `cuda:0`，使用现有 `.venv-astribot-inference` 作为候选环境，先核验 CUDA／PyTorch／模型依赖，记录环境快照。不要为部署覆盖现有仿真或训练环境。协议／调度逻辑不依赖 ROS 或 GPU，便于本机测试；SDK 包只在机器人执行器显式创建时导入并初始化。

## 2. 模型加载与数值契约

### 输入与输出

输入按 head、right wrist 顺序：1280×720×3、640×360×3 的 RGB uint8。处理必须与训练 reader 一致：先 RGB 解码，再 PIL BILINEAR 缩放至 224×224，并使用本次运行保存的 processor。SDK 若输出 BGR，只在采集边界转换一次。不要沿用旧右腕 640×480 的检查条件。

state 顺序：右臂关节 1～7、右夹爪反馈、头部关节 1～2。形状为 `(10,)`，送入模型时按其接口构造 `(1,1,10)`。手臂与头部为 rad，夹爪反馈为 SDK 连续刻度，可略超 0～100；只拒绝非有限值及违反已标定反馈合理范围的值，不机械截断为 0/1。

从运行目录 `data_contract.json/normalization` 读取 mean／scale，不能改用数据集全量 `meta/stats.json`。模型输出必须为 `(1,7,10)`；反归一化后响应为 `(7,10)`。不得额外做一帧动作偏移或扩展为仿真 action32。

服务返回原始反归一化预测，执行端仅在发送前将夹爪列 `<0.5→0`、`>=0.5→100`。记录原始值、二值判定和实际 SDK 目标。首版不添加隐式滞回；若实测抖动，另立版本验证。头部由模型输出，不默认用常量覆盖。任何替代、裁剪或动作修改都必须记入日志。

固定任务文本：`Press the down button while maintaining the demonstrated head posture.`。首版不接受任意外部任务文本。默认固定 seed=42 用于复现，记录每次 seed；更换随机策略必须单独比较。

### 权重加载

校验 checkpoint manifest 的 `model_sha256`、state/action_dim=10、horizon=7、processor 和归一化身份。加载完整训练权重时要求严格匹配，不能使用 `strict=False` 掩盖缺项，也不能重新初始化任何接口。模型 `eval()`、禁用梯度、`torch.inference_mode()`；以既有 BF16 autocast 推理为起点，保留训练权重精度，不先做量化。

分别记录首次加载、首次推理、warmup 后 p50/p95/p99、峰值显存。CUDA 计时须同步或使用正确的 CUDA event；不能只测异步调用返回时间。显存不足或延迟不达标时再评估优化，改变精度／推理步数后必须重新比较输出与任务效果。

## 3. 网络与消息协议

首版选择 HTTP/1.1 keep-alive＋二进制 NPZ，`allow_pickle=False`，单请求最多 8 MiB。直接传原始 RGB 数组以免引入第二次有损压缩；按实测带宽评估后续是否改为原始相机 JPEG 透传。模型同时最多处理一个请求，机器人只允许一个 in-flight；新的观测替换本地“待发送”槽，不形成排队积压。

5090 服务只监听 `127.0.0.1:8796`。首版通过工作站到 S1B 的反向 SSH 隧道让机器人访问自身 `127.0.0.1:8796`，不开放任意客户端的运动入口。隧道、桥接和模型服务分别有健康状态；SSH 重连不会自动重新启用执行器。

| 接口 | 内容 |
|---|---|
| `GET /health` | ready、协议版本、checkpoint step/hash、数据契约 hash、动作维度、horizon、设备信息 |
| `POST /predict` 请求 | `protocol_version`、`session_id`、`observation_id`、机器人 `observation_monotonic_ns`、head/right RGB、state10、各源原始时间及其已映射时间、seed |
| `POST /predict` 响应 | 原样返回 session/id/observation time；反归一化 `action_raw[7,10]`、`target_offsets_ns[7]`、模型／契约 hash、服务端预处理／推理耗时 |
| 错误响应 | HTTP 非 2xx，稳定错误码和简短信息；不能将异常替换成零动作、上一动作或随机动作 |

协议版本固定 `s1b-joint10-v1`。NPZ 字符串字段使用固定字符串类型数组，不使用对象数组。目标偏移为四舍五入后的 `(1..7)×10^9/30` ns。服务端不做机器人控制，也不把自己的 monotonic 时间当作机器人时钟。默认请求超时 1 秒，仅为影子模式通信初值；执行端动作到期保护独立工作，不能等待 HTTP 超时才停止。

模型或契约 hash 与会话握手不符、字段缺失、错误 dtype/shape、NaN/Inf、重复或乱序 observation_id 均拒绝。一次模型切换必须退出执行、创建新 session、清空队列并重新验证，不能在执行中热切换权重。

## 4. 机器人观测与时间基准

采集仅订阅已经核验的相机和部件状态话题；实时全身状态曾只有 20 维且缺失名字，禁止假定其与 HDF5 25 维拼接相同。使用部件限定映射，校验右臂 7、右夹爪 1、头部 2 的长度及单位；名字缺失时只能使用明确版本化的话题映射配置。

每个消息保留原 header、机器人接收 monotonic 时间和接收顺序。建立有限长度缓冲；以最新头部图像为锚点，选择当前缓冲中时间最接近的实测状态与右腕图像。首版不额外等待未来帧，不从缺失流复制上一条假装同步。

只有在可比时间域确认后，才应用跨流偏差门槛。候选工程初值：state 与 head ≤10 ms、right 与 head ≤40 ms、发送前 head 年龄 ≤80 ms。它们不是物理曝光延迟上限，需在影子运行报告中验证并固定。时钟发生跳变、流停更或不能映射到机器人 monotonic 时，观测无效。

部署中的 `observation_monotonic_ns` 取头部图像在机器人采集桥中的接收时刻；作为本版记录时间代理。所有目标 deadline 均在机器人本地计算。跨主机时钟不用于直接求动作年龄，5090 只返回耗时；避免直接相减两台机器的 monotonic 时间。

该代理与离线 MCAP log_time 不保证完全相同，需要比较接收延迟及抖动。曝光时刻标定未完成时，日志和验收报告必须保留这个限制；不能宣称“严格传感器同步”。

## 5. 动作调度

- 机器人控制线程与网络／推理解耦；以 30 Hz 作为策略目标消费节拍。SDK 内部伺服调用频率另行核验，不能把策略频率等同于底层控制频率。
- 一次预测的第 k 个目标时刻为原观测 monotonic 时间＋`(k+1)/30` 秒，而不是响应收到后重新开始计时。
- 响应收到时丢弃 deadline 已过去的目标。若 7 个全部过期，拒绝整个响应，不重放第一步，也不延长最后一步的有效期。
- 每个控制 tick 选择当前预测中最早的未来目标，且其 deadline 必须落在 `[tick,tick+1/30]` 内；不存在则不发送策略新目标，并进入明确的队列耗尽处理。记录计划 deadline、实际发送时间与相对误差。
- 收到更晚观测的有效预测时，用它替换旧预测尚未执行的部分；已发送动作不回滚。只接受当前 session、严格更新的 observation_id，丢弃迟到响应。
- 首版不做跨 chunk 混合或自定义轨迹插值。SDK filter 模式的行为与延迟必须先核验；任何低通／插值的引入均需记录配置、原始目标和修改后目标。
- 推理长期超过约 233 ms 窗口时，停止进入执行阶段；先优化链路或另行设计延迟补偿。不能仅靠降低消费频率继续使用原 30 Hz 训练时序。

影子分析同时统计“响应仍有未来点的比例”“选中第几步”“有效队列覆盖率”和控制 tick 抖动，不仅报告平均推理耗时。

## 6. 执行器与状态机

状态机：`DISCONNECTED → SHADOW → READY → EXECUTING`；错误进入 `FAULT`，正常结束进入 `STOPPED`。重新连接只回到 SHADOW。执行必须由本地操作者显式启用，启用绑定 session、模型 hash 和已验证的部署配置。

SHADOW 只预测和记录，禁止构造 SDK 控制客户端、申请控制权或调用运动 API。READY 是检查完成状态，不等于已获得控制权。首次进入 EXECUTING 时才按核验流程申请控制权；失败即退出。

按 SDK 部件映射传递三个列表：右臂 7、右夹爪 1、头部 2，目标为绝对位置。核查并固定 `set_joints_position(names, position, control_way, use_wbc, add_default_torso)` 的真实调用语义：不能仅因函数接受某个参数就认定不会联动躯干。未输出的底盘／躯干／左臂要采用经验证的保持方式，不发送仿真模板。

执行前校验关节限位、每周期目标变化、相对当前实测的偏差、头部允许区域、夹爪类别和观测时效。各限值按实际机器人配置与小幅试验填写，不以训练集 min/max 冒充硬件安全限位。超限拒绝整条命令并记录原因；不静默截断成看似正常的命令。

断线、过期响应、队列耗尽、SDK 异常、控制权丢失、非有限目标或人工停止均停止消费旧队列并进入 FAULT/STOPPED。具体“保持当前位置／调用停止接口／释放控制权”的顺序需要按 SDK 与机器人实际模式验证后配置；不默认重发最后一个未来目标，因为它可能继续驱动运动。停止和超时逻辑必须在机器人端独立运行。硬件急停保持可用，不依赖 5090 或 SSH。

## 7. 记录与开发产物

每次运行创建独立日志目录，保存配置及 hash、模型 hash、协议／SDK／代码版本、状态切换、请求编号、源时间、机器人接收／发送时间、推理耗时、实测状态、原始预测、选择的步号、实际 SDK 目标与故障原因。墙钟只作人工关联，调度使用 monotonic。

影子模式默认保存可回放观测片段及完整数值日志；明确图像保存频率、磁盘上限和丢帧计数。运动试验磁盘写入异常不能静默丢失执行证据，必须报告并按配置终止试验。视频和大日志放 `outputs/`，配置、测试和结果摘要进入版本控制。

开发交付还应包含操作手册：网口配置与连通性检查、环境启动、模型切换、只读连接、影子模式、显式启用、正常停止、断线恢复及日志分析。正式命令须在实现验收后填写，不把本计划里的拟定入口当作已经可运行。
