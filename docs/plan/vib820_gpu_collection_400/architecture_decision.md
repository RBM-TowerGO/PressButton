# 待确认的架构调整：每卡多个常驻单环境进程

状态：用户已于 2026-10-15 明确授权：“允许，按提案预检并完成采集（推荐）”。实施每卡多个常驻单环境进程，先测 1/2/4，全部原有验收门槛通过后自动采集、导出及验收 400 条。尚未取得生产 gate，不能将实现或预检计为正式数据。

## 为什么需要调整

本机 Isaac Sim 5.0 / Kit 107 的单进程多环境路径尚未通过图像验收：

- 同时显示完整场景副本，会让邻居房间进入部分相机，改变背景和光照。6 m 原排列以及多种较大间距排列均有失败证据。
- 七路同内参分组平铺解决了投影错误，但没有解决场景互相可见和部分复位后的渲染历史问题。相隔 24 m 的 8 环境最新对照在第二次复位被灯环残留检查拒绝。
- 按环境切换可见性，连续渲染到稳定的两环境静态试验通过，最大亮度差约 1.37%。但每个采样时刻切换环境的实际路径，虽然 20 次复位和 14 路 CPU/CUDA 像素一致性通过，仍出现不稳定的表面图像；相对完整单环境参考，左腕均值差约 30%。不能把稳定后单张图片的结果当成连续采集验收。
- 56 个独立相机产品同时活动的 8 环境试验出现 RTX ParameterBlock 资源分配错误。仅检查显存余量不能证明该路径可用。

证据在 `outputs/vib820_gpu_collection_400_preflight` 下的 `isolated_visibility_waited_probe`、`isolated_images_k2`、`matched_symmetric24_k8`、`layout_symmetric24_native_k8_probe`。所有这些均为预检，不计入 400 条。

## 可保留的已验证基础

`recording_gpu_pack_k1` 单环境通过完整按压物理审计、七路全帧解码、首次亮灯截断和 20 次重置。采集约 278.81 s；连同审计的一轮为 311.07 s，渲染约 201.47 s、物理 33.48 s、审计 32.17 s。启动和预检另计。

该轮 GPU 计算平均约 23.4%，峰值 56%；编码平均约 0.24%；显存峰值约 13.20 GiB。整机 CPU 平均约 100%，包括其他用户负载，不能全部归因于本采集器。此处是单环境诊断，既不是完整 1/2/4/8 sweep，也不是已达成双卡两倍加速。

## 拟实施方式

每个常驻进程仅持有一个完整场景和七路相机，持续服务多条候选，不为每条重新启动 Isaac Sim。每卡的进程数先测试 1、2、4；最大并发继续受显存 80% 和可用内存 32 GiB 的实测限制约束，不按显存线性估算直接投产。

这样能沿用已经通过完整录像验收的单环境图像路径，同时让多个进程并行准备控制、提交渲染和编码，避免通过更改材质、视场、分辨率或接触阈值解决图像问题。是否更快须实测，不预先承诺加速比。

实现需扩展当前 dispatcher 的 worker 标识和每卡进程数配置，将“worker ID”和“物理 GPU ID”分开；候选顺序选择、基础设施最多三次 attempt、物理失败不重试、原子提交和续采规则不变。生产 gate 必须冻结进程数、每进程一个环境及实际物理/渲染后端；吞吐统计按所有 worker 的真实重叠时间计算，不把单进程速度乘以进程数。

每个并发配置仍先预热，再实测至少两轮完整七路视频并审计。最终仍须达到相对旧四进程七路基线至少 2 倍，目标 3 倍；没有通过就停止在预检，不启动正式数据。当前没有任何新架构的吞吐结果。

400 条筛选、PCG64 候选序列、X/Y/yaw 范围、32 维字段、120/30 Hz、七路原始录像、官方 LeRobot v3 导出、20 条分层回放和所有磁盘规则保持原方案约定。
